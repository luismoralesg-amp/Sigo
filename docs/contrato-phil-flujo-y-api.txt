  Resumen
  Usamos el flujo de backend: la enfermera digitaliza, la paciente ve y comparte su historial
  con un código temporal, y el médico lo consulta solo mientras ese código esté vigente. El
  MVP son 12 pantallas y 18 endpoints, y el backend entrega primero respuestas de prueba
  con la forma final para que el frontend no se quede esperando.

          Qué es: una web app que se abre con un link en el celular o la computadora y se puede
          guardar como ícono. Funciona en celulares viejos y toma fotos aunque no haya señal.
          Stack: frontend en Next.js (PWA); backend en FastAPI con control de roles; Supabase
          para la base de datos, las fotos y el login del personal; IA de visión para leer las fichas;
          CAG local para las preguntas y los resúmenes.
          Tres roles: enfermera digitaliza y corrige; paciente solo ve, descarga y comparte
          (no edita ni borra); medico solo lee, con el código que le da la paciente o, en una
          emergencia, con un acceso limitado a alergias y condiciones crónicas.
          Nada se borra: corregir crea una versión nueva, y la foto o el archivo original queda
          guardado junto al dato.
          Extra: importar un Excel o Access viejo.
          Convenciones: JSON; campos en español y snake_case ; fechas YYYY-MM-DD ; fecha y
          hora en ISO 8601 con zona -06:00 ; todo bajo /api/v1 .

  La paciente es la que da el permiso: el médico solo ve el expediente con el código que ella
  genera, y el acceso se cierra solo. Si la paciente no tiene smartphone, la enfermera genera
  el código o se lo manda por SMS; si llega inconsciente, el médico abre un acceso de
  emergencia que solo muestra alergias y condiciones crónicas. La enfermera nunca borra;
  cada corrección es una versión nueva. Si no hay señal al escanear, la foto espera en el
  celular y sigue el mismo camino cuando vuelve la conexión.

  Modelos de datos
  Estos tipos son el contrato: el backend responde con esta forma exacta y el frontend la
  usa tal cual. Una ficha en papel puede traer varias consultas de distintos años, así que la
  extracción devuelve una lista. Cada consulta y los datos del paciente tienen número de
  versión, porque corregir nunca borra.

     // Un dato leído por la IA. "baja" = se pinta en amarillo y la enfermera lo
     revisa primero.
     type Campo<T> = { valor: T | null; confianza: "alta" | "baja" };


     type Rol = "enfermera" | "medico" | "paciente";

     type Centro = {
        id: string;
        nombre: string;              // "Puesto de Salud Aldea Chuicacá"

     // Para paciente, centro = null y paciente_id = su id.
     type Usuario = { id: string; nombre: string; rol: Rol; centro: Centro | null;
     paciente_id: string | null; debe_cambiar_pin: boolean };

  Contrato de API
  Todas las rutas van bajo /api/v1 , reciben y devuelven JSON (salvo la subida de fotos y
  las descargas) y piden Authorization: Bearer <token> . El personal usa el token de
  Supabase y la paciente el que le da POST /auth/paciente . El backend saca el rol del
  token y revisa los permisos; el frontend nunca manda el rol.

  Enfermera
  3. GET /pacientes/buscar?dpi=2547896310801 → { "pacientes": [Paciente] } , o {
  "pacientes": [] } si no existe. Devuelve 200 con lista vacía, no 404 .

  4. POST /pacientes con { "dpi", "nombre", "fecha_nacimiento", "sexo",
  "comunidad", "telefono" } → 201 con { "paciente": Paciente, "pin_inicial":
  "482193" } . El PIN se muestra una sola vez para que la enfermera se lo dé a la paciente. Si el
  DPI ya existe, responde 409 .

  5. POST /pacientes/{id}/fichas , en multipart/form-data :

           client_id : UUID que genera el celular al tomar la foto. Si llega dos veces, el backend
          devuelve la ficha que ya existe con 200 .
           imagenes : uno o más JPEG en orden de página, reducidos por el frontend a 1600 px
          de lado y menos de 1.5 MB cada uno.
           capturada_en : fecha y hora de la foto (puede ser horas antes si estuvo sin señal).

  Responde 202 con la ficha en procesando . Si la IA es rápida, puede responder directo
  con lista y la extracción; el frontend acepta las dos.

  Expediente
  10. GET /pacientes/{id}/expediente → Expediente . Para el médico, el backend revisa
  que tenga un acceso vigente para ese paciente y registra la consulta en la bitácora; el
  frontend no manda nada extra. Con acceso de emergencia devuelve solo los datos del
  paciente y las alertas, con la lista de consultas vacía. Sin acceso vigente responde 403
  con acceso_vencido .

  11. GET /consultas/{id}/versiones → { "versiones": Version[] } , de la más nueva a
  la más vieja.

  Paciente
  12. GET /pacientes/{id}/exportar?formato=pdf → el archivo, con Content-
  Disposition: attachment . Formatos: pdf , docx , xlsx , txt , md y html . Para el demo

  Cada código sirve una sola vez y se puede canjear durante 10 minutos; el acceso que abre
  dura 2 horas. Lo puede pedir la paciente desde su celular, o la enfermera desde el puesto a
  pedido de la paciente (queda en la bitácora). Con { "enviar_sms": true } el backend
  también lo manda por SMS al teléfono registrado, para quien solo tiene un celular básico.
  En modo demo, el acceso dura 2 minutos.

  16. GET /pacientes/{id}/accesos → { "accesos": Acceso[] } , el más reciente

  Médico
  14. POST /codigos/canjear con { "codigo": "K7P-4Q2" } → { "paciente_id":
  "p_12", "acceso_vence_en": "2026-11-21T12:45:00-06:00" } . Si el código venció
  responde 410 ; si ya se usó, 409 .

  15. POST /pacientes/{id}/preguntar con { "pregunta": "¿Cuándo fue su última
  vacuna?" } → { "respuesta": "…", "fuentes": Fuente[] } . Si no hay fuente, la
  respuesta dice que no lo encontró; nunca inventa. Pide acceso vigente, igual que el
  expediente.

  18. POST /emergencia con { "dpi": "2547896310801", "motivo": "Llega
  inconsciente a emergencias" } → { "paciente_id": "p_12", "acceso_vence_en":
  "2026-11-21T11:45:00-06:00", "tipo_acceso": "emergencia" } . El motivo es
  obligatorio, con al menos 10 caracteres. El acceso dura 1 hora y solo deja ver los datos del
  paciente y las alertas; versiones, asistente y descargas responden 403 con
   solo_emergencia . Queda en la bitácora de la paciente marcado como emergencia, con el
  motivo.

  Reglas que ambos lados tienen que respetar:

      1. Nada se borra. No hay DELETE en la API. Corregir crea una versión nueva y la anterior
          queda en GET /consultas/{id}/versiones .
      2. La IA nunca guarda sola. Nada entra al expediente sin POST
          /fichas/{id}/confirmar . Lo que la IA no lee va con valor: null y confianza:
          "baja" ; jamás un valor inventado.
      3. El médico entra con código o por emergencia. Sin un acceso vigente, todo lo del
         paciente responde 403 . El acceso se cierra solo al llegar a acceso_vence_en , y el
          frontend muestra cuánto le queda. El acceso de emergencia pide un motivo, dura 1
          hora y solo muestra alertas.
      4. La paciente solo ve, descarga y comparte. Cualquier escritura con su token responde
         403 .
      5. Sin señal no se pierde nada. El frontend guarda la foto y el client_id en el celular y
          reintenta al volver la señal; un client_id repetido devuelve la ficha existente.
      6. El DPI tiene 13 dígitos. El frontend lo valida al escribirlo y el backend lo vuelve a
         validar.
      7. La bitácora es del backend. Canjear un código, abrir el expediente y cada pregunta al
         asistente quedan registrados sin que el frontend haga nada.
      8. El PIN nunca viaja de vuelta. Solo se muestra una vez, en la respuesta de POST
          /pacientes , y el backend lo guarda cifrado. La paciente lo cambia la primera vez que
          entra.
